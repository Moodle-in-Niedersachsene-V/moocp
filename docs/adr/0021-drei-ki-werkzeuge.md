# E21 Drei KI-Werkzeuge: Claude Code, Codex CLI, LM Studio

Status: gilt. Die Regeln dazu stehen im Index der [CLAUDE.md](../../CLAUDE.md).

## Entscheidung

Die App braucht von einem Client dreierlei: MCP über einen lokalen Befehl (stdio, die Brücke) und damit den Kanal nur für das eigene Konto (E6), Skills im Format `SKILL.md` (E8) und eigene Werkzeuge für Dateien, weil alles Gelesene im Arbeitsordner liegt (E5). Das haben Claude Code, Codex CLI (OpenAI) und LM Studio mit seinem Agenten Bionic. Die Skills bleiben für alle dieselben und sagen nichts, was nur in einem Client gilt.

Je Werkzeug eine Unterklasse von `KiWerkzeug` (`lib/einrichtung.dart`):

- **Claude Code** trägt über `claude mcp add-json` ein (`{"type":"stdio","command":<Brücke>,"args":["--profil",<Name>],"timeout":…}`), weil nur dort das Zeitlimit (`timeout`) mitgeht; das gilt auch für einen stdio-Server.
- **Codex** über die Datei, weil `codex mcp add` kein Zeitlimit je Werkzeugaufruf (`tool_timeout_sec`) kennt; die App schreibt nur den eigenen Block `[mcp_servers.<Servername>]` in `config.toml` (`command`, `args`, `tool_timeout_sec`), ohne TOML-Paket (E14).
- **LM Studio** heißt hier sein Agent Bionic (eigenes Programm, Datenordner `~/.lmstudio` geteilt mit dem klassischen LM Studio). Gemessen: Bionic liest `~/.lmstudio/mcp.json` nicht, sondern seine eigene Liste `apps/bionic/.internal/ng-mcp.json`; es startet Server nur als lokalen Befehl (stdio); weder `lmstudio://add_mcp` noch `bionic://add_mcp` tragen dort ein; und es übernimmt eine von außen geänderte Liste sofort, auch während es läuft, und startet einen neuen Server binnen einer Sekunde, beim eigenen Start also oft lange bevor moocp läuft. Darum schreibt die App ihren Eintrag selbst in diese Liste, und zwar die Brücke `moocp-bruecke.exe --profil <Name>` (`bin/moocp_bruecke.dart`, `lib/mcp/bruecke.dart`). Die Messungen zu Bionic stehen im Kommentar zu `LmStudio` in `lib/einrichtung.dart`, der Aufbau der Brücke im Kopf von `bruecke.dart`; warum nicht `codex mcp add`: im Kommentar zu `CodexCli`.

Die Brücke ist für alle drei Werkzeuge auf jedem System derselbe Weg zur App: Sie findet den Kanal des Profils selbst, prüft Ordner, Socket oder Pipe und die Gegenseite (E6) und reicht die Werkzeugaufrufe als zeilenweises JSON-RPC an den MCP-Server der App weiter, eine Verbindung je MCP-Sitzung; ein Geheimnis steht in keinem Eintrag. Sie ist ein eigenes Programm ohne Flutter und eine einzige Datei, weil ein Client sie offen hält, solange er läuft: Unter Windows legen Installer und Bau sie dann beiseite (E15), statt zu scheitern. Die Prüfung des Servers unter Windows geht über die Prozessnummer hinter der Pipe ([E6](0006-nur-lokal.md), dort das Restrisiko). Beim Anmelden schickt sie das `initialize` des Clients an die App und danach `notifications/initialized`; die App sieht darin den Namen des Clients (Protokoll, `status`). Reißt die Verbindung ab (die App wurde beendet oder neu gestartet), bekommt jede Anfrage, die noch auf ihre Antwort wartete, eine Fehlerantwort und wird nie wiederholt: Ob die App sie schon ausgeführt hat, ist unbekannt, und ein Werkzeug schreibt in Moodle. Die nächste Anfrage baut die Verbindung neu auf. Endet stdin, wartet die Brücke höchstens drei Sekunden auf Antworten und schließt dann die Verbindung; laufende Aufrufe brechen ab. Ein offener Freigabedialog schließt sich damit spätestens drei Sekunden, nachdem der Client sein Rohr geschlossen hat (E4); ein schreibender Aufruf, der schon in Moodle läuft, wird dadurch nicht abgebrochen, nur seine Antwort geht verloren, und sein Ausgang bleibt über E37 geklärt. Damit es gleich ist, wann Bionic sie startet, hängt nur der Werkzeugaufruf an der App: `initialize` und `tools/list` beantwortet die Brücke selbst und reicht dabei durch, was `moocp.exe --werkzeugliste` dazu sagt – immer die installierte Version, ob die App läuft oder nicht –, `ping` ohnehin. Auf Linux und macOS öffnete `moocp --werkzeugliste` die Oberfläche der App (das Fenster ginge für jeden Start der Brücke auf); dort liegt die Liste deshalb je Profil als Datei `werkzeugliste-<Profil>.json` im privaten Ordner des Kanals, die die App bei jedem Start und nach dem Start der Plugins schreibt (0600) und die Brücke nur liest, wenn Ordner und Datei dem Konto allein gehören. Nach einem Update zeigt sie bis zum ersten Start der neuen App die alte Liste. Läuft die App beim Werkzeugaufruf nicht, startet die Brücke sie und wartet bis zu fünf Minuten auf die Anmeldung (E13: der MCP-Server läuft erst danach) – kürzer als Bionics Zeitlimit, damit die KI den Hinweis bekommt, dass moocp noch nicht bereit ist, statt nur einer Zeitüberschreitung. Einen Aufruf, den der Client inzwischen abgebrochen hat, reicht sie nicht mehr weiter. Die Brücke bedient jedes Instanzprofil ([E31](0031-mcp-server-je-instanz.md)) über ihr Argument `--profil`; in Bionic bekommt jedes Profil einen Eintrag mit seinem Namen. Die Werkzeugliste gilt je Profil: `moocp.exe --werkzeugliste --profil <Name>` unter Windows, `werkzeugliste-<Name>.json` auf Linux und macOS, mit den Werkzeugen der Plugins, die in diesem Profil eingeschaltet sind (E35); jede Brücke kündigt so genau an, was der Server ihres Profils kann.

Weil Bionics Liste intern und undokumentiert ist: nur Einträge mit dem Namen eines Profils anfassen, über eine Zwischendatei schreiben, eine unlesbare nie überschreiben, und im Dialog „eingetragen“ sagen, nicht mehr – ob Bionic den Eintrag annimmt, zeigt erst die Verbindung im Protokoll. In allen Clients gilt: Eine Datei, die sich nicht lesen lässt, wird nie überschrieben, und angefasst werden nur die Einträge der App (die Servernamen der Profile), nie andere des KI-Werkzeugs. Skills liegen je Werkzeug in dessen eigenem Ordner (`~/.claude/skills`, `~/.codex/skills`, `~/.lmstudio/skills`): Claude Code liest keinen gemeinsamen Ordner, und nur so bleibt das Deinstallieren eindeutig. Welches Werkzeug sich verbunden hat, steht im Protokoll und in `status`.

Bionic gibt außerdem Bilder aus Werkzeugergebnissen nicht ans Modell weiter, weder als Bildinhalt noch als eingebettete Ressource (darum Bildschirmfotos als Dateien, E18), verlangt in jeder Sitzung eine Erlaubnis für den Arbeitsordner, die sich nicht vorab eintragen lässt, und bricht einen Werkzeugaufruf nach seinem Zeitlimit ab, auch während eine Freigabe offen ist; den Abbruch meldet Bionic, die Brücke reicht ihn weiter, und der Dialog schließt sich (E4).

Ein solches Zeitlimit haben alle drei Clients, ohne Angabe 60 Sekunden ab dem Aufruf – Lesen und Schreiben eines größeren Abschnitts brauchen schon je fast so lange, und die Freigabe läge dazwischen. Die App trägt deshalb überall 35 Minuten ein (`clientZeitlimit` in `lib/einrichtung.dart`), länger als die Frist einer Freigabe, damit diese zuerst endet und nach einer späten Freigabe noch Zeit zum Schreiben bleibt: bei Claude Code als `timeout` im JSON von `claude mcp add-json`, bei Codex als `tool_timeout_sec = 2100`, bei Bionic als `connection.timeoutMs`. Ein Eintrag ohne passendes Zeitlimit gilt als veraltet und wird beim nächsten Einrichten ersetzt. Bei Claude Code und Codex prüft der Einheitentest nur die Eintragung; das Verhalten einer offenen Freigabe am Gerät ist dort noch nicht gemessen.

Der Hinweis zum Datenschutz gilt für jedes Werkzeug: LM Studio kann auch Cloud-Modelle benutzen, Claude Code und Codex lassen sich auf andere Anbieter umstellen. Dialog und README sagen deshalb „an das eingestellte Modell“, nie „bleibt auf dem Rechner“.

## Auf dem Mac

Claude Code und Codex CLI starten dieselbe Brücke wie unter Windows (`moocp-bruecke`, in der App unter `Contents/MacOS`). Die Skill-Ordner sind `~/.claude/skills` und `~/.codex/skills`; `CODEX_HOME` verlegt Codex wie unter Windows. LM Studio mit Bionic wird auf dem Mac nicht angeboten, weil es Bionic dort nicht gibt ([E24](0024-plattformen.md)). Dart übersetzt nur für die Architektur des Baurechners; die universelle App braucht die Brücke der anderen Architektur dazu (`tool/mac_bau.sh`). Der Datenschutzhinweis gilt auf dem Mac genauso.

## Verworfen

Loopback-HTTP mit Schlüssel im Eintrag für Claude Code und Codex (siehe [E6](0006-nur-lokal.md): Ein anderes Konto kann den Port vor der App belegen und bekäme Schlüssel und Aufrufe); die App selbst als Brücke (`moocp.exe --mcp-stdio` – Bionic hielte exe, DLLs und `data\` gesperrt, und Update wie Neubau scheiterten, solange es läuft); für Bionic die Lehrkraft moocp zuerst starten zu lassen (ein Schritt mehr, und Bionic läuft oft den ganzen Tag) oder moocp mit der Brücke zu starten (ginge bei jedem Start von Bionic mit auf und meldete sich bei Moodle an); eine Werkzeugliste als Datei, die die App beim Start ablegt (nach einem Update veraltet, bis die neue Version lief, und ob sie es ist, verrieten nur Größe und Zeit der exe) – nur unter Windows; auf Linux und macOS gibt es keine Abfrage der App ohne Oberfläche, dort gilt die Datei im privaten Ordner; dem Client geänderte Werkzeuge zu melden (`notifications/tools/list_changed` – kein anderer Client bekommt das, nach einem Update gilt überall: neue Sitzung); die ChatGPT-App (erreicht nur öffentliche HTTPS-Server; der Weg über OpenAIs Tunnel machte die Werkzeuge von außen erreichbar, gegen E6, und brächte trotzdem keinen Zugriff auf den Arbeitsordner); Ollama (Modellserver, kein MCP-Client); für Bionic das Eintragen von Hand (zu viel für Lehrkräfte), `mcp-remote` als Brücke (braucht Node.js, lädt fremden Code aus npm, und der Schlüssel stünde im Klartext in Bionic) und das Beenden von Bionic vor dem Schreiben (unnötig, es liest die Liste im laufenden Betrieb neu); ein gemeinsamer Skill-Ordner `~/.agents/skills` (Claude Code liest ihn nicht, und ein geteilter Ordner machte das Deinstallieren mehrdeutig; eine Entscheidung „E30“ dafür gibt es deshalb nicht); Verzeichnis-Junctions auf einen Ordner (hängt an einer Windows-Eigenheit, das Deinstallieren müsste sie von echten Ordnern unterscheiden); ein Geheimnis in den Pfad oder die Argumente der Brücke zu legen (es stünde in jedem Protokoll, das Pfade schreibt, A4); Hinweise an die KI in `status`, Skills oder Werkzeugantworten, die Erlaubnis anzufordern oder die Bilder zu öffnen (ein schwaches Modell folgte ihnen nicht, ein starkes braucht sie nicht, und sie kosten Kontext), ebenso Bedienhinweise für schwache Modelle in der README (wer eines wählt, lebt damit; die README bliebe sonst nicht lesbar).
